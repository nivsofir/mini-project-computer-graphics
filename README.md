# Procedural Cyberpunk City

A real-time, fully procedural 3D cyberpunk city rendered in the browser with
[Three.js](https://threejs.org/) / WebGL. No external 3D models, no
Blender assets, no backend — every building, texture, road, vehicle and
light is generated by code at runtime from a single integer seed.

Built as a university Computer Graphics mini-project.

## Running it

```bash
npm install
npm run dev
```

Open the printed local URL (typically `http://localhost:5173`).

```bash
npm run build     # production build to dist/
npm run preview   # preview the production build
```

## Troubleshooting: low FPS

If the FPS readout in the UI is stuck low (e.g. ~20) despite the scene
being lightweight (this app targets 60fps and typically runs at several
hundred on real hardware with acceleration on), check that your browser
is actually using your GPU before assuming it's a code/scene problem:

1. Go to `chrome://gpu` (Edge: `edge://gpu`, Firefox: `about:support`)
   and look at **Graphics Feature Status** → **WebGL**. If it says
   *"Software only, hardware acceleration unavailable"*, the browser is
   rendering on the CPU instead of the GPU — no amount of scene
   optimization fixes that, since it's not a code issue.
2. Go to `chrome://settings/system` and make sure **"Use graphics
   acceleration when available"** is switched **on**, then relaunch
   Chrome. This was the actual cause the one time this came up during
   development — hardware acceleration was simply toggled off in Chrome
   settings, despite a real dedicated GPU being installed and working
   fine. Turning it on took the app from ~20fps to 170–180fps with zero
   code changes.
3. If it's already on and `chrome://gpu` still shows software
   rendering, check `chrome://gpu`'s **"Problems Detected"** section for
   a specific blocklist/driver reason, or try a clean GPU driver
   reinstall.
4. If you're on a VM or a Remote Desktop/RDP session, software
   rendering is often expected behavior (no GPU passthrough) rather than
   something fixable from the browser.

The app also logs its actual GPU string and per-frame draw call/triangle
counts to the browser devtools console a couple of seconds after load,
which is useful for confirming whether a slowdown is a real scene-cost
issue or an acceleration/environment issue.

## The seed system

Every generation decision that shapes the city — building dimensions,
building archetype, facade window pattern, neon sign text/color, rooftop
props — is drawn from `utils/SeededRandom.js`, a small
[mulberry32](https://gist.github.com/tommyettinger/46a874533244883189143505d203312)
PRNG seeded with a single integer. The same seed always reproduces the
exact same city. Road layout, camera path, sky and distant skyline are
intentionally *not* seed-dependent — they're part of the fixed world the
seeded city sits inside.

Traffic and pedestrians use plain `Math.random()` since their motion is
ambient set-dressing, not part of "the city" a seed is meant to reproduce.

## Performance approach

The original prototype gave every building its own `BoxGeometry` and a
*cloned* window texture, meaning hundreds of draw calls and hundreds of
duplicate GPU texture uploads for what were visually only a handful of
distinct patterns. The current architecture instead keeps draw calls to a
small, roughly constant number regardless of city size:

- **Buildings**: every building's geometry is generated in CPU memory with
  its facade UVs and a per-building vertex-color tint already baked in,
  then bucketed by which of 6 shared window textures it uses and merged
  (`BufferGeometryUtils.mergeGeometries`) into one `BufferGeometry` per
  bucket — **6 draw calls for every building facade in the city**.
- **Rooftop / ground-floor props** (antennas, comm towers, AC boxes, glow
  strips, landmark spires, entrance lights): one `InstancedMesh` per prop
  *type* — a handful of draw calls for however many props exist.
- **Roads**: asphalt, sidewalks, curb neon (×2 colors) and painted lane /
  crosswalk markings are each one merged mesh — 5 draw calls for the
  entire road network, regardless of grid size.
- **Traffic & pedestrians**: each is a single `InstancedMesh` (plus one
  more for the traffic light-trails) — one draw call per system, whether
  there are 10 vehicles or 500.
- **No per-frame allocations**: `Vector3`/`Matrix4`/`Quaternion`/`Object3D`
  helpers used inside the render loop (camera, traffic, pedestrians) are
  created once and reused every frame.
- **Bloom**: `UnrealBloomPass` is deliberately run at a quarter of the
  screen's pixel count (see `rendering/PostProcessing.js`) — bloom is
  blurry by nature, so the resolution cut is effectively invisible but
  meaningfully cheaper.

## Project structure → Computer Graphics concepts

| File | Concept(s) demonstrated |
|---|---|
| `city/BuildingGenerator.js` | Procedural modeling (6 building silhouette archetypes built from stacked/scaled boxes), transformations |
| `city/ProceduralTextures.js` | Procedural texturing via the Canvas 2D API (window facades, neon signs, glow halos, ground/road panels) |
| `city/CityGenerator.js` | Procedural modeling, instancing, geometry merging, Z-buffer / hidden-surface rendering |
| `city/RoofDetails.js` | Instancing (one `InstancedMesh` per rooftop/facade/entrance prop type, incl. industrial pipes/vents) |
| `city/NeonSigns.js` | Procedural texturing, instancing (shared glow-halo mesh) |
| `environment/Roads.js` | Procedural modeling, texturing, animated UV offset (flowing neon pulse) |
| `environment/Traffic.js` | Instancing, transformations, animation |
| `environment/Pedestrians.js` | Instancing, animation |
| `environment/Rain.js` | Particle systems (`LineSegments` streaks, not points), animation |
| `environment/RainSplashes.js` | Particle systems (pooled/recycled `Points`, per-vertex alpha fade) |
| `environment/Lightning.js` | Lighting (animated intensity spikes) |
| `environment/Sky.js` | Vertex-color gradients, transformations |
| `environment/SkylineSilhouette.js` | Instancing, fog |
| `camera/CinematicCamera.js` | Catmull-Rom splines, arc-length parameterization (`getPointAt`), quaternions / SLERP, perspective camera & `lookAt` transformations |
| `rendering/PostProcessing.js` | Post-processing pipeline, bloom |
| `rendering/VignetteShader.js` | Custom fragment shader (vignette + chromatic aberration) |
| `rendering/ReflectionProbe.js` | Environment mapping (`CubeCamera`), reflections |
| `utils/SeededRandom.js` | Reproducible procedural generation |

## Scope

Deliberately excludes anything outside a browser-based CG mini-project:
no multiplayer, no backend, no database, no physics engine, no NPC AI,
no imported 3D models. Everything on screen is generated procedurally at
runtime by this codebase.
